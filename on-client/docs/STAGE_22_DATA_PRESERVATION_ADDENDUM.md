# 22단계 데이터 보존 판정 보완 — 저장 위치·안전한 절차·한계

이 보충 문서는 `STAGE_22_DATA_PRESERVATION.md`의 긴 절차 중 판정 요청에 해당하는 내용을 한곳에 요약합니다. 코드에서 확인한 저장 계약과 이 PC에서 실제 실행한 결과를 구분합니다. 현재 DB 경로, 설정 파일, 사용자별 파일의 존재 여부는 확인하지 않았으며, 백업·복구도 실행하지 않았습니다. 비밀값, 사용자 경로, 설정 원문, DB 내용은 제출물이나 대화에 붙이지 마세요.

## 데이터 종류와 저장 위치를 찾는 방법

| 데이터 | 코드에서 확인한 위치·방식 | 실제 경로를 확인하는 방법과 한계 |
|---|---|---|
| 조치 요청·상태·감사 이력 | 호스트가 지정한 **이미 존재하는 단일 SQLite 파일**에 `alekov_action_intents`, `alekov_action_state`, `alekov_action_audit` 테이블을 추가합니다. DB 파일 전체에는 이 앱이 소유하지 않는 데이터도 있을 수 있습니다. | `src/server.mjs`는 `--alekov-actions-config <설정 파일 경로>`를 명시한 경우에만 조치 기능을 구성합니다. 그 설정의 `databasePath`가 대상입니다. 기본 경로·자동 검색·자동 생성은 없습니다. 일반 `tools/start-alekov.ps1`은 이 조치 플래그를 전달하지 않습니다. 따라서 호스트 운영자에게 조치 기능 사용 여부, 설정 파일 위치, DB 경로를 확인합니다. 모르면 저장소나 사용자 폴더를 검색하지 않고 실제 DB 경로는 미확인으로 둡니다. |
| 조치 정책·DB 경로 설정 | 호스트가 `--alekov-actions-config`로 지정하는 닫힌 설정 파일입니다. 설정에는 `schema`, `databasePath`, `policy`가 있습니다. | 설정 경로는 프로젝트 코드에 고정돼 있지 않습니다. 서버를 실행한 호스트 운영자가 알려 준 경로만 사용합니다. 설정 전체를 출력·공유하지 말고, 원래 계획의 2절 절차로 로컬에서 `databasePath`만 확인합니다. |
| native 로그인·계정 연결 설정 및 등록 이력 | `tools/start-alekov.ps1`이 프로젝트 경로의 SHA-256을 계산해 현재 Windows 사용자 Profile 아래 `.aleph-keshev-<해시>`를 정합니다. 코드상 구성은 `native.json`, `registry\\.alekov-native-registry.json`, `vault\\.alekov-owner.json`, 문맥별 `vault\\<contextFingerprint>.credential`입니다. | 이것은 코드가 계산하는 경로·파일 계약이지 이 PC의 존재 증거가 아닙니다. 원래 프로젝트 폴더와 동일 Windows 사용자 문맥에서 원래 계획 7절의 **읽기 전용 존재·ACL 확인**을 사용할 수 있습니다. 검사 요약 외의 경로·파일명·설정 내용은 공유하지 않습니다. |
| 앱 자격 정보 | vault 기록은 `tools/app-credentials.ps1`에서 Windows DPAPI `CurrentUser`로 보호되고 사용자·프로젝트 문맥에 결속됩니다. | 제공 코드에 학생용 export/import 또는 다른 사용자·PC로 옮기는 검증된 백업/복원 명령은 없습니다. 파일을 단순 복사하는 것을 백업·복원 절차로 간주하지 않습니다. |
| SDP 개인 연결 설정·자격 | 서버에 별도 `--sdp-host-config`를 지정할 때 운영자가 지정한 경로의 설정과 자격 파일을 사용합니다. | 학생 프로젝트가 이 PC의 실제 경로나 개인 자격 존재를 확인해 주지 않습니다. 경로·자격을 찾아 출력하거나 백업 파일에 넣지 않습니다. |
| 사용자·기기·사건·취약점 조회 결과 | 앱 API가 연결 원천에서 받아 화면에 반환합니다. 이 검토에서 해당 조회 결과를 장기 보관하는 별도 학생 DB 계약은 확인하지 못했습니다. | 실제 원천의 보존·백업 정책은 프로젝트 문서만으로 확정할 수 없습니다. |

## SQLite DB: 가능한 백업과 별도 복구 확인

아래 절차는 조치 DB 사용 여부와 실제 경로를 호스트 운영자가 확인해 준 경우에만 가능합니다. 서버를 정상 종료하고, 저장소 밖의 **이미 존재하며 현재 Windows 사용자만 접근 가능한** 백업·복구 폴더를 사용합니다. 폴더의 소유자와 ACL을 확인할 수 없으면 진행하지 않습니다. 경로를 추측하거나 DB를 새로 만들지 않습니다.

1. 원래 계획 [`STAGE_22_DATA_PRESERVATION.md`](STAGE_22_DATA_PRESERVATION.md)의 **2절**을 따라 호스트가 알려 준 조치 설정에서 `databasePath`만 로컬에서 확인합니다. 호스트가 설정 위치나 DB 경로를 확인해 주지 못하면 중단합니다.
2. 서버를 정상 종료합니다. 원래 계획 **3절**의 PowerShell/Node.js 절차를 사용해 기존 SQLite 파일 전체를 고유한 새 파일로 백업합니다. 절차는 현재 사용자 전용 ACL을 통과한 기존 폴더만 허용하고, 원본과 새 사본의 `PRAGMA integrity_check`를 확인합니다.
3. 절차가 성공해도 이는 검사 시점의 SQLite 구조 검사이지 업무 데이터 정합성, 실제 앱 결과, 백업 매체의 장기 보존을 보증하지 않습니다. DB 전체를 민감한 데이터로 취급하고 경로·데이터를 문서나 대화에 남기지 않습니다.
4. 별도 복구 확인은 원래 계획 **4절**대로 기존 백업을 또 다른 새 경로의 SQLite 파일로 복사한 뒤 무결성과 조치 테이블 구성을 확인하는 범위입니다. 백업 원본과 운영 DB를 덮어쓰지 않습니다.

**중요한 복구 한계:** 위 4절은 새 파일로 복원해 읽기 구조를 확인하는 비파괴 복구 시험입니다. 운영 DB를 과거 사본으로 교체하거나 `databasePath`를 과거 DB로 바꾸어 서비스에 다시 연결하는 복구 절차가 아닙니다. `src/actions/README.md`는 조치 테이블 rollback이나 전체 DB 복원을 하지 말라고 명시합니다. 이전 상태로 되돌리면 조치 상태·감사 이력이 후퇴하거나 이미 전달된 작업의 재전송 위험이 있으므로, 이 프로젝트가 안전한 운영 rollback을 지원한다고 안내할 수 없습니다. 운영 DB 복구가 필요하면 원천 조치 상태와 데이터 정합성을 호스트 운영자가 판단·승인해야 합니다.

## 사용자별 설정: 원본 보존은 가능하지만 앱 수준 백업·복구는 미지원

- **기존 설정을 잃지 않기:** 원래 프로젝트 폴더, 원래 Windows 사용자 계정/프로필, 프로젝트 경로를 유지하고 설정 파일을 편집·삭제·이동하지 않습니다. 실행 도구가 설정을 확인하지 못하면 복사나 재설치를 시도하지 말고 중단합니다.
- **별도 파일 백업/복원:** 제공 코드에 설정 export/import 기능이 없습니다. DPAPI `CurrentUser`, 사용자 SID, vault 식별자, 프로젝트 경로·디렉터리 identity와 ACL 결속 때문에 `.aleph-keshev-*`의 개별 파일을 다른 사용자·PC·새 프로젝트 위치에 단순 복사해 복구할 수 있다고 보장할 수 없습니다. 임의 `Copy-Item`/`robocopy`를 검증된 복구 방법으로 제시하지 않습니다.
- **관리되는 Windows 사용자 프로필 백업:** 조직 관리자가 실제 백업 수단이 같은 사용자 SID와 DPAPI 복호화 조건, ACL, 원래 프로젝트 경로 및 디렉터리 identity를 보존하는지 사전에 확인하고 승인한 경우에만 그 관리 절차를 따릅니다. 프로젝트에서 이 수단의 백업·복원은 시험하지 않았습니다. 복원 뒤 읽기 전용 존재·ACL 확인을 할 수 있지만, 그것만으로 자격 복호화·로그인·외부 연결 성공이 입증되지는 않습니다.
- 이 조건을 충족하는 관리 절차가 없다면 사용자별 설정의 별도 백업·복구는 **현재 코드에서 미지원·미검증**입니다. 지원하지 않는 절차를 성공 가능한 것처럼 만들어 적지 않습니다.

## 현재 확인 상태

| 항목 | 상태 |
|---|---|
| 저장 종류·코드상 경로 계산·조치 DB 설정 입력 | 관련 시작 도구, `src/actions/README.md`, `src/actions/store.mjs`, `src/actions/action-startup-config.mjs`, `src/server.mjs`, vault 코드를 읽어 확인 |
| 이 PC의 조치 기능 활성 여부·설정 위치·DB 파일 경로 | 미확인. 호스트 운영자 확인 전에는 검색하지 않음 |
| 이 PC의 사용자별 파일·ACL 및 SDP 설정 | 미확인. 파일 내용·개인 경로를 출력하지 않음 |
| SQLite 백업·별도 복구 시험과 결과 | 미실행. 위 단계는 문서화한 절차이며 수행 증거가 아님 |
| 사용자별 설정 이관·복원 | 프로젝트 코드에서 지원된 방법을 확인하지 못함. 관리자 프로필 절차도 미시험 |

따라서 이 보완은 판정 요청의 저장 위치와 **실제로 가능한 DB 파일 백업·별도 복구 확인 절차 및 운영 복구의 한계**를 명시합니다. 사용자별 설정은 코드가 보장하지 않는 파일 복사나 복구를 만들어 내지 않고, 원본 보존과 미지원 경계를 구분합니다. 이 문서 보완만으로 22단계가 통과했다고 볼 수 없으며, 새 판정 결과를 확인해야 합니다.
